LicoUp 只有一个应用身份、安装名称和数据根目录。`nightly` 与 `stable` 是同一身份的
发布轨道，不是并行安装的应用，也不是分发传输类型；`direct` 与 `app-store` 仍是
打包传输值。

## 转换所有权与固定端点

原生迁移 owner 将最后已发布产品的持久格式转换为计划发布的格式。内嵌 frontier
目录是唯一源/目标对的权威，[兼容性说明](../COMPATIBILITY.zh-CN.md)展示该目录。
产品版本号不一定等于其发布二进制实际记录的格式标识；必须保留已记录的标识与
已发布步骤前缀。本地构建或 schema 修正不会建立新的受支持发布。

存储 owner 定义物理 schema 和转换。启动准入与独立原生工具复用这些 owner，
不建立第二套格式写入实现。独立程序为 `crates/licoup-migrate`：单个 Rust
二进制，无需 Node.js 或已安装客户端即可运行。发布分发必须提供可单独下载的
制品，而不是永久捆绑的包。其命令为 `inspect`、`plan`、`convert`、`resume`、
`export`、`import`、`rehearse`、`converters`、`package-convert` 与
`package-resume`。每次调用输出一份 JSON 报告，并在仍有未完成工作时以非零状态
退出。`inspect`、`plan` 与 `converters` 只读；`convert`、`resume`、`export`、
`rehearse`、`package-convert` 与 `package-resume` 都要求操作者给出
`--writers-stopped` 声明。

`export` 与 `import` 到达与已安装客户端 `backup` 命令相同的 Foundation
完整数据根归档 owner：任一端写出的归档都能被另一端恢复，双方都不持有第二套
归档格式。`rehearse` 在一次性工作根上驱动同一批 owner，报告实际执行的每个
阶段，并且不改动源，因此可以在获授权的真实数据转换之前验证转换与两种明文
容器的往返。已退役的 Node.js 包不作为转换器、兼容入口或回退保留。仓库保留的
诊断是开发工具，不是另一个受支持的转换权威。没有任意历史目标选择或降级
转换合同。

导入先由 Foundation 验证并解包，再在其私有暂存载荷中准备保管元数据、属主
管理的引用和修订保护。这些属主检查在任何载荷发布到空目标目录之前完成。
物理暂存路径只用于验证；持久化引用指向最终逻辑主目录。Foundation 重新验证
载荷的边界和不跟随链接约束，并在发布时保留已验证的只读保护。暂存清理、发布
回滚和目录同步由同一属主负责并检查。入口始终持有选定主目录的写者协调。多文件
发布不是崩溃原子的激活事务：操作被中断或回滚不完整时，目标仍是未验证状态，
不是可用恢复。应保留该目标用于诊断，并从未改变的源归档重试到新的空主目录。
导入不会选择或激活恢复后的主目录。

在提供该工具的发布中，`LicoUp-migrate-macos-arm64` 及其 `.sha256` 从该发布
按需下载，取得后可离线运行。本地发布目录负责暂存工具和校验和；这不证明制品
已经发布或可以从已发布标签获取。安装或更新客户端不会安装、替换或移除已经
下载的工具，运行中的客户端也绝不会选择捆绑的迁移器。应选择其声明源和目标
符合所需转换的发布。替换可执行文件不会重置进度：转换日志保留在选定数据根中。

两个 macOS 发布配置均选择受治理的 `independent-tool` 与
`independent-tool-digest` 配对，来源为独立发布工具构建输出，绝不来自应用包。
Apple Release 负责该配对的 Developer ID 签名、独立公证、不可变材料固定及公开
字节/校验和验证，不会通过运行迁移工具来探测验收。源码配置与合成检查不证明
制品已公开可用或操作系统首次运行验收已通过；相应属主合同必须经过合法采用，
受治理发布才能消费它。

显式维护要求写者停止且源可恢复。短期启动 `admission.lock` 不能证明运行写者
已经停止。独立工具在转换、续行、导出、导入和演练期间持续持有客户端选定主目录
的独占进程租约；遇到参与协调的活跃写者时拒绝操作，而不是停止该写者。操作者
声明仍负责覆盖旧客户端和不参与协调的其他写者。获授权的真实数据转换必须先
保留源，并在一次性数据根演练，不能用
活跃存储调试目标 schema。受保护凭据继续遵守平台托管和授权边界。

转换按域记录持久进度。已提交的物理存储优先于过期 marker 或 journal；恢复
对账已完成步骤，不重复转换。所有数据库、文件和操作系统凭据库不构成一个
原子事务。依赖业务数据的转换失败仍遵循向前 `migration_step_failed` 执行/重试
策略；只读结构预检不证明每个已存业务值均有效。

## 包自有的转换声明

拥有持久格式的包在自己的 manifest 中声明该事实。可选的 `conversion` 声明给出转换器
类型、包载荷内的入口、该转换器可读取的已发布源格式，以及它产出的目标格式。本契约
只发布一种转换器类型 `native-executable`：程序由包自身携带；需要解释器的转换器会借用
包并未携带的运行时。不拥有任何格式的包不带该字段——多数包不执行转换——因此字段缺失
表示声明完整，而不是空声明；被要求提供转换却未声明的包会被拒绝，报告中给出该包自身
的 id 和所需源格式，且不含私有数据。

转换声明在任何执行之前先做结构校验，每条拒绝都指明被违反的规则：非原生转换器类型、
位于包载荷之外的入口、空的源格式列表，以及缺失或格式错误的目标格式，各有稳定错误码。
[manifest schema](../../schemas/extensions/manifest.schema.json) 发布相同的字段、模式和
边界，schema 一致性套件将其与本 crate 双向固定，第三方按该 schema 校验时会被主机实际
执行的规则拒绝。

转换声明与经过认证的发布元数据描述同一组事实。已发布的包携带
`licoup.package-release.v1` 声明，其 `converter` 对象给出转换器类型、入口、一个源格式
和目标格式，发布索引按包发布该对象。已提交的固件位于
`tests/fixtures/client_package_release/fixture-native-converter/`，它在两份文档中声明
同一个转换器，其 manifest 列出其发布声明所命名的源格式。

独立工具读取该声明，而不是识别它编译时内置的格式。`licoup-migrate` 的 `converter` 模块
从客户端内嵌 frontier 目录取得所需端点对——与启动准入使用的同一个唯一源/目标对——
读取某个包的 manifest，并回答哪个包拥有该端点对。识别过程不查询任何客户端版本：哪些
客户端构建可以加载某个包（`compatibility`）与该包拥有哪些格式是两个独立主张，因此为
另一客户端版本线发布的包仍然拥有其格式，源支持也绝不从已安装旧客户端的版本推断。
即使一个包携带原生转换器，只要其声明的格式不是所需端点对，就会被拒绝；工具不保存
任何包名或格式别名表。给定包根目录时，工具还会检查 manifest 承诺的入口确实是该根目录
内的文件。

## 协调式包转换

独立工具负责协调一次从包仓库到转换器再返回的转换。除包自身的程序外，没有任何东西转换
数据：工具只做选择、暂存、运行、验证与记录。

### 已安装转换器清单

`licoup-migrate converters --package-store <root>` 读取包仓库记录的已安装版本，并报告每个
版本对所需端点对的候选资格。只有当包自身的 manifest 声明了该端点对时，它才是**候选**：
所需源格式是它发布的格式之一，且目标格式恰好是所需目标。未声明任何转换的包（大多数包）
不是候选，声明了其他端点对的包也不是；两者都会以指明所违反规则的拒绝码报告。包的
compatibility 列表不参与判断：哪些客户端构建可以加载某个包属于宿主的准入问题，而不是格式
问题。

选择是确定性的：所选身份的最大已安装版本；未指定身份时取所有候选中的最大版本。无论哪种
情况都会列出全部候选，使操作者看到可选方案。当调用方提供已签名发布索引时，候选还必须正是
该索引发布的载荷：两个发布角色签名都要在规范化未签名字节上验证通过，条目与已安装 manifest
在身份、版本、入口、类型与端点对上一致，且宿主为已安装字节记录的摘要与大小等于索引发布的
摘要与大小。索引每个包只发布一个源格式，而 manifest 声明其可读取的列表，因此对账规则是：
发布的源格式必须是所需源格式，且是 manifest 所声明的格式之一。不是已发布载荷的候选会被
拒绝，而不会被运行。

### 转换器协议

`licoup-migrate package-convert`（以及 `package-resume`）将选中的入口作为有界原生子进程运行：

```text
<entry> --source <dir> --target <dir> \
        --source-format <identity> --target-format <identity> \
        --result <file> [--resume]
```

* `--source` 是数据根的暂存副本。转换器只读取它，且不得在其中写入。
* `--target` 是产出转换结果的目录，也是该进程的工作目录。工具从不删除它，包括跨恢复时。
* `--result` 是转换器写入 `licoup.package-conversion-result.v1` 文档的位置：`schema`、
  `sourceFormat`、`targetFormat`、`complete`，以及可选的 `convertedRecords`。
* `--resume` 表示上一次调用被中断，必须继续既有的 target 而不是重新开始。

工具对它未编写的程序施加边界：捕获输出有上限，超出部分报告为已截断；结果文档有大小上限且
形状严格；子进程运行在自己的进程组中，因此停止会覆盖整棵进程树；环境被缩减为原生程序在
该平台启动所需的变量。不存在自动执行截止时间：流逝的时间不是用户的决定，因此由调用方停止
它不再需要的运行。转换器可以是任意规模的程序，但必须是包载荷内的原生可执行文件——借用
解释器的转换器在声明阶段即被拒绝，工具与转换都不访问网络，也不需要已安装的 Agent、旧包
运行时、Node 或 Python。

完成与否以转换器自身、并经过检查的报告为准，绝不只看退出状态：进程必须以零退出，结果文档
必须是文档化形状并指明所需端点对，`complete` 必须为真，且 target 不得为空。任何不符都会让
本次运行保持未完成，工具的退出状态保持非零。在收到的源目录内写入的转换器会被拒绝，且每次
运行后都会验证数据根摘要未变：转换只暂存副本，绝不写入源根。

### 中断、恢复与准入

工具现有的运行记录负责保存进度。该记录写入调用方的工作根，与暂存副本和 target 并列，记录
包身份、版本、入口、所需端点对、本次运行据以准入的已安装载荷摘要，以及运行读取源根时的
源根摘要。记录两个步骤：暂存源副本与运行转换器。每步在尝试前写入、在落定后重写，因此中断
会表现为未落定的步骤，而不是某种声明。

未落定的运行只会被继续，绝不被重新开始。对已记录未落定运行的普通 `package-convert` 会被
拒绝（`package_conversion_unfinished`）并指明恢复方式；恢复要求同一已声明包、端点对、载荷
摘要与源摘要，会复用完整的暂存副本而不是重新暂存，并要求转换器使用 `--resume` 继续它已经
产出的 target。已落定的运行回答 `alreadyCurrent`，不会被第二次转换。被中断或失败的转换是
未完成的工作，绝不是成功的迁移。

在任何暂存之前都会先询问维护准入。工具读取宿主自身的空闲准入决定
（`domain/work_admission`），当本宿主仍拥有未完成的本地工作时拒绝
（`maintenance_work_unfinished`），或在另一维护操作持有闭门准入屏障时拒绝
（`maintenance_admission_closed`），并报告它读到的决定与阻塞 owner。操作者的
`--writers-stopped` 声明覆盖该协调之外的写入者，与客户端 owner 各动词完全一致；运行时工具
持有客户端选定数据主目录的独占进程租约。

离线载荷通过包仓库既有路径导入：`--payload` 由仓库自身的制品准入做有界预检，在提供签名索引
时校验其内容摘要，并由仓库的 `install_local_import` 按 manifest 身份与权限范围发布。已安装
的同一版本若摘要相同即满足导入；记录摘要不同的版本会被拒绝，而不是被静默替换。

不属于本契约的部分：把产出的 target 发布回数据根。独立转换产出暂存 target 并报告它；替换已
安装的数据根是另一项需要单独授权的动作，工具绝不写入它读取的源根。发布索引工具在打包载荷
时尚未读取 manifest 的 `conversion` 块，且其 `converter.sourceFormat` 是单个格式而 manifest
声明的是列表；读取方对二者做对账并拒绝不一致，因此两个文档互相矛盾的发布无法被转换。

## 客户端更新选择

原生制品内嵌产品版本、发布轨道和不可变状态迁移前沿。本地开发构建默认为 Nightly；
可分发构建必须显式提供轨道。更新只比较 SemVer 优先级：Nightly 自动接受严格更新的
Nightly，也可显式选择严格更新的 Stable；Stable 只自动接受严格更新的 Stable；
相同或更旧版本一律不合格，Stable 不选择 Nightly。

签名的 manifest-v2 绑定目标轨道和每个版本的准确迁移前沿。人工迁移说明只供阅读；
调用方不能覆盖运行版本、运行轨道、前沿或迁移步骤。

成功读取官方公开 Stable 发布信息后，即使该发布尚无更新清单，也可以确认其版本不高于
运行版本。这只是公开版本观察，不携带已验证密钥、制品或替换回执。更新版本、未知版本
或 Nightly 缺少清单时，报告更新资料不可用。只要清单存在，无论发布标签是什么，都必须
验证其签名。网络与完整性错误保持为失败，过期缓存不能掩盖验证失败。每次检查开始时，
先清除旧候选回执，再采用新的检查结果。

替换前，原生更新验证会写入候选认领，并绑定所选版本、目标轨道、准确前沿和制品回执。
新二进制必须在迁移准入前匹配该认领；不匹配会在任何状态修改前阻断。当前更新器通过
安装同一候选或具备更高向前能力的候选恢复已认领的替换，不授权数据降级。

## 启动准入

桌面生命周期解析原始数据目录后，必须先调用原生状态准入，之后才能加载工作区、偏好
设置、会话、Adaptive Flywheel、Mobile Relay 或其他产品状态。准入锁定数据根，探测
所有域，证明迁移链连续，并在第一次模式修改前写入产品版本高水位。每个持久步骤通过
原子文件替换或所属数据库事务提交；只有权威后置条件持久化后才更新有界账本。
Canonical Conversation 与 Adaptive Flywheel 的 SQLite 元数据、工作区与展示偏好文档、
Mobile Relay 配置及其余声明的偏好文档，都在各自权威存储中探测。marker 只为不存在的
存储记录对账事实，绝不能替代对已存在存储的探测。

在高水位、frontier 或域 marker 推进前，SQLite 准入验证完整的保留 owner 结构：
列、空值约束、默认值、主键和唯一键、CHECK 表达式、部分索引谓词、外键动作、
排序规则及其他写入约束。定义来自实际 owner DDL。受支持的旧 Conversation
结构先在内存中仅升级 schema，再与完整合同比较，而不是只检查启动所需列。
按需创建的工作流表可以缺失，但已存在的错误结构必须拒绝。已发布 producer
产生的 nullable terminal 变体仍有效。无法识别的结构不会被静默修复或猜测为
语义等价的 SQL。

保留的 JavaScript evaluator 使用相同 owner DDL 和结构升级步骤。SQLite 检查
错误限制在相应域内，不会将不可读存储判为健康，也不会丢失其他域观察。独立
冻结夹具验证原生准入、实际 owner 读写及真正的诊断 evaluator。owner 与夹具
变更通过模块目录选择这些已有回归套件。

`gateway-credential-custody` 域是该前沿中的受保护后续步骤。尚无托管完成回执的 macOS 数据根通过
`pendingAuthorizationDomainIds` 报告待授权状态，客户端仍可就绪；启动准入不打开
钥匙串。空数据目录不能证明钥匙串中没有旧条目。显式 `llm-gateway credentials migrate`
执行[密钥托管](../protocols/llm-gateway.zh-CN.md#密钥托管)定义的保护迁移，成功后才写入
完成 marker 并对账同一份迁移账本。失败或取消保持待迁移状态。托管操作使用独立的锁，
原生授权弹窗不会阻塞其他启动准入。

当前域会跳过，再次运行不会修改。核心状态领先于二进制、核心未知形状、迁移缺口、核心步骤不完整
或失败才拒绝整个启动，并只返回稳定且不泄露隐私的错误码。崩溃后已提交步骤会从权威状态
对账，不会重复执行。持久用户与安全状态绝不会被静默重置。

Native 构建会从同一份声明式状态机资源生成 update handoff 与 Adaptive Flywheel
artifact 的状态类型和迁移表。handoff owner 校验并持久化生成的 pending 到 claimed
迁移；strategy store owner 通过现有 SQLite 迁移 API 执行生成的状态转换。这些模块负责
准入副作用，生成表仍是唯一的迁移权威。

当前准入实现可通过重新安装同一已验证且具备能力的构建，或安装更新的签名构建后重试
恢复。高水位推进后旧二进制会被拒绝，不会降低元数据让旧二进制打开新存储。

### 工作流存储转换

当前源码将 Adaptive Flywheel 的 SQLite schema 从 2 升至 3，准入 frontier 从 1 升至 2。
现有 migration owner 一次性显式化历史隐式入口槽和效果路由；转换与 schema marker
在同一 SQLite 事务提交。只准入真实发布的 schema 2 和当前 schema 3 结构；
已完成 frontier 1 的 ledger/marker 通过注册的下一步继续升级。

这次转换保留 revision/semantics 身份、run 快照、命令 attempt、租约和授权。不可变
包字节保持原摘要；包校验先验证原身份，再解释历史格式。普通编译只接受 canonical
定义，不改写定义。这项向前转换不建立额外的历史兼容格式。

## 发布

Nightly 从 `nightly` 分支准备，并使用固定的 `nightly` 预发布；Stable 继续从
`release` 产生不可变的 `v{version}` 版本。两种配置都保留 `land.lico.licoup`、
`LicoUp.app` 和共享数据根。Stable 必须不是预发布且版本严格更新，因此相同版本的
Stable 不会被提供。
发布验证按 SemVer 优先级比较版本（构建元数据不能打破平局），拒绝迁移前沿回退，并在
签名前校验共享应用身份。

### 启动必要性

Frontier 的 `startupScope` 将核心和可选功能区分，独立于持久性。可选文档失败通过
`unavailableFeatureDomainIds` 返回，不覆盖文件，也不伪记为当前格式；Flutter 对应步骤
保留内存默认值或保持功能关闭，核心数据失败仍拒绝。未使用的历史表和入向关系可共存，
不读取或删除；空库正常初始化，完整当前结构验证后可重建缺失标记并保留原行。遵循
[启动与保留数据规则](../RUNBOOK.md#startup-and-retained-data)。
