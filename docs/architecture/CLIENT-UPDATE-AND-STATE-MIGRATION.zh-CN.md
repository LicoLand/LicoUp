LicoUp 只有一个应用身份、安装名称和数据根目录。`nightly` 与 `stable` 是同一身份的
发布轨道，不是并行安装的应用，也不是分发传输类型；`direct` 与 `app-store` 仍是
打包传输值。

## 独立迁移 CLI

数据迁移是一项独立维护和分发的 Node.js CLI 能力。计划源码位于 `tools/data-migration/`，
拥有自己的包、版本、可下载制品和发布流程，无需额外仓库才能实现这种独立性。
无论安装了哪个客户端版本，包括客户端无法启动或未安装的情况，
用户都能自由下载、安装、运行、升级和卸载该工具。卸载工具保留应用数据及恢复记录。

工具必须支持从任意已发布的数据版本升级到当前版本，也支持将新版本数据回退到任意
已发布的旧目标版本。历史格式读写器以及可组合的升级、降级步骤必须跨工具版本持续保留。
源版本从实际存储探测，用户指定的目标版本决定采用哪一版已发布的数据契约；运行中的
客户端版本及其内嵌迁移前沿不能限制工具选择源版本或目标版本。

降级必须生成目标客户端实际可打开的数据。旧格式无法表达的数据应保留为可恢复的扩展，
并明确报告表达差异；不能静默丢弃，也不能仅恢复旧备份就声称已完成当前数据的转换。
只有目标存储满足后置条件后才能更新准入信息，不能只修改版本 marker 就让旧客户端读取
新格式数据。

Node.js CLI 负责协调版本转换，受保护密钥继续遵守平台原生托管和授权边界。需要的原生
辅助程序随独立工具分发，不能依赖已安装的客户端。工具与客户端分别发布，并持续保留
历史版本的下载制品和转换定义。

以上是独立工具的设计约束，工具尚未实现。下文描述当前客户端的更新与准入实现；这些
向前更新限制不能作为独立 CLI 所支持源版本、目标版本的限制。

### 与工作流重构的集成

工具纳入本次工作流编译器和宿主重构。现有 `client-update-manifest.mjs` 只产生更新
元数据，不是数据转换器。独立 CLI 提供检查、转换规划、转换和恢复操作；探测实际
store，按版本化数据合同选择步骤，不依赖运行客户端或执行 Graph。

CLI 协调转换，格式探测与 codec 由现有 native migration owner 统一维护，启动准入
和工具自带的专用 helper 复用。将该 owner 拆为模块，不复制 reader 或新建迁移权威。
helper 随计划中的 Rust 1.95.0 基线编译，保留原生托管和授权。

读取活跃数据根前，经所属宿主的 Proxy/控制路径请求维护、排空受影响工作，达到实际
安全交接后才取得根独占所有权。当前短期 `admission.lock` 不能证明全部运行写者已停。
共同根访问协议必须覆盖宿主、CLI 和 helper；后台迁移不能抢占活跃 invocation 或
按计时器强杀。没有活动 owner 时，工具不要求安装客户端。

转换按持久域记录进度，验证目标后置条件后才改变准入元数据；崩溃后对账已提交步骤，
不重复执行。不能宣称所有数据库、文件及 OS 凭据库天然处于一个原子事务。

版本合同覆盖工作流定义/run、排队命令/投递、订阅/游标、节点控制、后继交接、未知
效果、用量事实及端点状态引用。历史 reader/writer、转换步骤和有意义夹具永久保留；
它们是工具支持能力，不是被取代的客户端实现。

旧目标无法安全表达记录时，把完整记录及关系保存在旧客户端发现和执行路径之外的
恢复扩展中，明确报告旧客户端不能操作这些状态；只有语义真实时才产生不执行的目标
投影。不能将未知效果改成可重试、待执行或已完成来适配旧 schema。之后选择有能力
版本时恢复原语义；未知效果对账与数据格式转换是不同操作。

所有已发布目标仍可选择转换。只有无法取得一致源、无法安全隔离保全实际外部效果，
或受保护托管不可满足时，才阻塞相关步骤。旧格式本身不支持新状态，应通过保全处理，
不能静默丢失数据或永久拒绝其余转换。目标客户端实际读取、转换中断、历史往返及
保全记录不会被执行，均需实施后的合成夹具证据。

### 降级、继续编辑与再次升级

转换场景包含新版、降级、旧客户端实际编辑/删除/执行，再次升级。保全扩展不得
覆盖新事实、复活删除或重放历史效果；须按原身份和修订与当前 store 对账后恢复。
不认识新锁协议的旧进程不会被新锁隔离，独占须通过其实际生命周期与数据根所有权
取得。协议及密钥状态遵循固定 SDK 的恢复合同，与普通数据库回滚分开。
该场景仍是独立迁移 CLI 的待实施要求。

## 客户端更新选择

原生制品内嵌产品版本、发布轨道和不可变状态迁移前沿。本地开发构建默认为 Nightly；
可分发构建必须显式提供轨道。更新只比较 SemVer 优先级：Nightly 自动接受严格更新的
Nightly，也可显式选择严格更新的 Stable；Stable 只自动接受严格更新的 Stable；
相同或更旧版本一律不合格，Stable 不选择 Nightly。

签名的 manifest-v2 绑定目标轨道和每个版本的准确迁移前沿。人工迁移说明只供阅读；
调用方不能覆盖运行版本、运行轨道、前沿或迁移步骤。

成功读取官方公开 Stable 发布信息后，即使该发布尚无更新清单，也可以确认其版本不高于
运行版本。这只是公开版本观察，不携带已验证密钥、制品或替换回执。更新版本、未知版本
或 Nightly 缺少清单时，报告更新资料不可用。只要清单存在，无论发布标签是什么，都必须
验证其签名。网络与完整性错误保持为失败，过期缓存不能掩盖验证失败。每次检查开始时，
先清除旧候选回执，再采用新的检查结果。

替换前，原生更新验证会写入候选认领，并绑定所选版本、目标轨道、准确前沿和制品回执。
新二进制必须在迁移准入前匹配该认领；不匹配会在任何状态修改前阻断。当前更新器通过
安装同一候选或具备更高向前能力的候选恢复已认领的替换。显式数据降级由上述独立迁移
CLI 负责。

## 启动准入

桌面生命周期解析原始数据目录后，必须先调用原生状态准入，之后才能加载工作区、偏好
设置、会话、Adaptive Flywheel、Mobile Relay 或其他产品状态。准入锁定数据根，探测
所有域，证明迁移链连续，并在第一次模式修改前写入产品版本高水位。每个持久步骤通过
原子文件替换或所属数据库事务提交；只有权威后置条件持久化后才更新有界账本。
Canonical Conversation 与 Adaptive Flywheel 的 SQLite 元数据、工作区与展示偏好文档、
Mobile Relay 配置及其余声明的偏好文档，都在各自权威存储中探测。marker 只为不存在的
存储记录对账事实，绝不能替代对已存在存储的探测。

`gateway-credential-custody` 域是该前沿中的受保护后续步骤。尚无托管完成回执的 macOS 数据根通过
`pendingAuthorizationDomainIds` 报告待授权状态，客户端仍可就绪；启动准入不打开
钥匙串。空数据目录不能证明钥匙串中没有旧条目。显式 `llm-gateway credentials migrate`
执行[密钥托管](../protocols/llm-gateway.zh-CN.md#密钥托管)定义的保护迁移，成功后才写入
完成 marker 并对账同一份迁移账本。失败或取消保持待迁移状态。托管操作使用独立的锁，
原生授权弹窗不会阻塞其他启动准入。

当前域会跳过，再次运行不会修改。状态领先于二进制、未知形状、迁移缺口、步骤不完整
或失败都会关闭启动，并只返回稳定且不泄露隐私的错误码。崩溃后已提交步骤会从权威状态
对账，不会重复执行。持久用户与安全状态绝不会被静默重置。

当前准入实现可通过重新安装同一已验证且具备能力的构建，或安装更新的签名构建后重试
恢复。高水位推进后旧二进制会被拒绝。显式降级需要独立 CLI 先完成存储转换并建立目标
版本可用的准入状态，再允许旧客户端打开；这项集成尚待实现。

### 工作流存储转换

当前源码将 Adaptive Flywheel 的 SQLite schema 从 2 升至 3，准入 frontier 从 1 升至 2。
现有 migration owner 一次性显式化历史隐式入口槽和效果路由；转换与 schema marker
在同一 SQLite 事务提交。更早的存储先经过原步骤到 schema 2；已完成 frontier 1 的
ledger/marker 通过注册的下一步继续升级。

这次转换保留 revision/semantics 身份、run 快照、命令 attempt、租约和授权。不可变
包字节保持原摘要；包校验先验证原身份，再解释历史格式。普通编译只接受 canonical
定义，不改写定义。这项向前转换不表示独立 CLI 或其降级合同已经实现。

## 发布

Nightly 从 `nightly` 分支准备，并使用固定的 `nightly` 预发布；Stable 继续从
`release` 产生不可变的 `v{version}` 版本。两种配置都保留 `land.lico.licoup`、
`LicoUp.app` 和共享数据根。Stable 必须不是预发布且版本严格更新，因此相同版本的
Stable 不会被提供。
发布验证按 SemVer 优先级比较版本（构建元数据不能打破平局），拒绝迁移前沿回退，并在
签名前校验共享应用身份。
