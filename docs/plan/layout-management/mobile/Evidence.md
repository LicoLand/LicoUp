# Mobile Layout Renderer Evidence

## Declaration-derived mobile product

The mobile plan does not prescribe a profile count. For the `N` profiles registered by the production composition, the mobile surface requires exactly one private mobile bundle per profile. Entries and evidence roots are discovered from typed definitions rather than maintained as a second list.

Adding a profile adds its own `profiles/<profile>/mobile/` implementation and one composition registration. Existing profiles and layout-management algorithms do not change.

## Frozen no-redesign evidence

The current worktree render is authoritative for appearance, arrangement, navigation, composer clearance, semantics, focus/traversal, motion, and interactions. Catalog-enumerated Home, Agents, and Settings production fixtures cover every registered mobile bundle.

Profile-owned behavior, adaptive/lifecycle, semantic/accessibility, interaction, golden, and normalized source-manifest suites pass without a post-freeze golden refresh.

## Isolation closure

- mobile shell chrome, navigation, destination presentation, previews, tests, and goldens are profile-private;
- profiles consume only neutral contracts, palette input, and immutable semantic ports;
- no sibling import, complete controller/controller scope, shared styled chrome/metrics, profile-ID renderer branch, backend/platform/native implementation import, mutable registration, or compatibility fallback is reachable;
- per-surface pairwise verification is generated as `N(N − 1)` directed sibling assertions, while aggregate verification derives `B(B − 1)` from `B = N × M`;
- retired layout names and namespaces are reset, not discovered or migrated.

## Migration rationale and ownership consequence

The pre-migration mobile audit found uneven bundle/golden/manifest evidence and shared presentation/controller reach-through that could couple sibling renderers. That gap justified disjoint shell/component, destination/bundle, preview, test, golden, and manifest ownership. Bundle completeness remains distinct from central registration, live switching, current-state enforcement, build, simulator/device, and launch proof.

Independent Android build verification follows shared Flutter changes. Device installation and launch occur only when an authorized device is available and are reported separately from build success.

## Evidence limits

Mobile renderer evidence is separate from Android/iOS build, simulator/device, packaging, release, and store claims. Receipts exclude local paths, user content, device identity, backend runtime data, credentials, secrets, and ciphertext.
