# Catalog-Driven Layout Isolation Evidence

The exact inventory is discovered from typed profile definitions and runtime surfaces. It is evidence for a delivery, never a cardinality rule. The plan uses `N` registered profiles, `M` declared surfaces, and exactly `N × M` owned bundles.

## Correction audit observation

On 2026-07-15, the correction audit observed `N = 4` registered profiles and `M = 2` declared runtime surfaces in the then-current tree, yielding `8` profile/surface pairs. This is a one-run observation explaining the detected plan drift. It is not a target, default, limit, fixture assumption, or proof of the corrected architecture; every later run must rediscover all three values.

The same audit found that earlier closure receipts were not sufficient for the corrected contract. Open findings include shared styled presentation policy, shared widget/controller reach-through, a separately maintained profile-identity inventory in verification paths, incomplete production state/focus and persistence-race evidence, and stale visual receipts or diagnostics. The active correction Node owns these gaps; none is considered closed merely because an earlier fixed-inventory command passed.

## Typed inventory authorities

- Profile definitions at the production composition root are the runtime profile-identity authority.
- `layout_environment.dart` defines runtime surfaces and surface-local viewport policy.
- `built_in_layout_composition.dart` is the sole production registration join.
- `layout_catalog.dart`, `layout_definition.dart`, and `layout_registry.dart` validate and index the declared product.
- Canonical profile directories are enumerated by verification and must equal the registration identity set; that enumeration is not persisted as a second identity list.

The plan intentionally does not repeat the current names or count. Adding a profile contributes only its private surface bundles plus one typed composition registration; management, Settings, host, and verification algorithms remain unchanged.

## Required isolation closure

| Boundary | Proof required before the correction Node can close |
| --- | --- |
| Exact product | Composition derives registered definitions and typed surfaces, requires one immutable bundle for every member of their Cartesian product, and rejects empty, duplicate, missing, extra, or revision-inconsistent declarations. Directory discovery must equal the registration identity set. |
| Private presentation ownership | Concrete shells, navigation, status, destination presentation, components, tokens, metrics, previews, fixtures, and profile goldens resolve only below the owning profile/surface trees. |
| Neutral ports | Immutable semantic snapshots/actions and neutral palette input replace styled shared presentation, complete-controller exposure, and platform reach-through. |
| Identity neutrality | Profile IDs remain immutable registration data. No behavioral or styling switch, conditional, factory, or lookup map branches on a known ID, and no second identity inventory exists. |
| Complete migration | Superseded shared styled chrome/presentation policy, complete-controller scopes, fixed-subset manifest mechanisms, stale diagnostics, and compatibility paths are absent. |
| Dynamic verification | Boundary and visual-manifest gates discover `N`, `M`, and `N × M`; mutation self-tests cover arbitrary added profiles and surfaces, cardinality drift, directory/registration mismatch, ownership overlap, forbidden transitive imports, and identity branches. |
| State/default authority | Manager and resolver consume one injected preferred default; selection transactions, current-schema recovery, bounded profile/surface state, semantic focus, and serialized appearance/locale writes have current tests. |

## Findings retained as correction rationale

The audits found shared styled chrome and visual metrics, complete controller/platform reach-through, profile-ID decisions in shared Agents/Settings code, scattered concrete presentation ownership, uneven or stale per-profile manifests/tests/goldens, and fixed-identity assumptions in verification. These findings remain open until current post-correction gates prove the required closure above; this document does not infer implementation completion from intended architecture.

## Frozen design evidence required

The pre-correction worktree, not historical fixed-subset receipts, is the visual input. The migration must compare every discovered bundle against its frozen pre-correction evidence and must not refresh the baseline after correction work begins to conceal a renderer difference.

Post-correction evidence must cover pixels, behavior, adaptation, lifecycle, semantics, keys, keyboard/touch interaction, safe insets, state, and deterministic previews. Source manifests must traverse transitive visual inputs, and pairwise ownership/change-impact checks must be generated from the discovered product.

## Earlier receipts and current evidence status

Earlier Nodes recorded passing aggregate layout, representative baseline, composition, catalog, registry, manager, resolver, host, Settings, boundary, visual-manifest, formatting, and analysis commands. The correction audit supersedes those receipts for final acceptance because they predate the corrected cardinality and ownership contract. They remain historical observations only.

The active correction Node has no checked acceptance criterion yet. Its commands, post-correction visual comparisons, macOS rebuild/open, and independent Android build/device handling must be rerun and recorded before a new delivery claim is made.

## Evidence limits

Evidence is minimum necessary and excludes machine identity, local paths, user content, device identity, accounts, credentials, secrets, ciphertext, and backend runtime data. Build, launch, device install, packaging, GitHub Release, and store publication remain separate claims.
