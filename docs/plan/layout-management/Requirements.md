# Layout Management Foundation Requirements

Upper constraint: [`../product-scope/Requirements.md`](../product-scope/Requirements.md). Layout work may present only the canonical default scenarios and optional-plugin boundary; it cannot add product capabilities.

## Product problem

Lico Arc needs a layout-management authority that scales with the registered product: `N` semantic profiles across `M` runtime surfaces produce `N × M` independently owned surface bundles. Layout selection remains a presentation concern. It cannot duplicate business state, alter client capabilities, hide reachable workflows, or let one bundle's implementation change another bundle's rendering.

The current worktree rendering is the no-redesign baseline recorded in `Evidence.md`. This plan may isolate, register, persist, and verify those layouts, but it shall not restyle, rearrange, rename visible product labels, or remove current interactions.

## Users and workflows

- Users choose any registered layout from Settings, preview it without restarting, keep or cancel the preview, and return to their current task without losing navigation, conversation, draft, focus, or long-running operation state.
- A selected semantic profile resolves to the independently implemented bundle for the active runtime surface and viewport policy.
- Maintainers can develop any one of the `N × M` bundles without importing, restyling, rebuilding from, or changing any of the other bundles.
- Adding a profile requires only its independent surface directories and bundles plus one composition registration. It shall not require edits to another profile, the manager/resolver algorithms, catalog/registry implementation, host, or Settings logic.

## Requirements

- **REQ-001 — Semantic layout profiles.** The client shall accept an immutable registered set of `N ≥ 1` stable semantic profile identities with localized product labels and exactly one catalog default. Numbered, versioned, legacy, alias, and compatibility identities are not allowed. First run, reset, loading recovery, manager fallback, and resolver fallback shall share one injected `LayoutProfileDefaults.preferredForPlatform` authority whose value must be a registered identity; the unique catalog default remains metadata and shall not become a competing fallback authority.
- **REQ-002 — Complete registered product and whole-presentation ownership.** For `N` profiles and `M ≥ 1` registered runtime surfaces, composition shall require exactly `N × M` immutable surface bundles. All renderer production files shall be concentrated below the canonical root `frontend/layout/profiles/<profile>/<surface>/`; tests and assets shall use corresponding profile/surface-owned roots. Each bundle owns shell/navigation composition, destination presentation, styled chrome, component recipes, non-color visual tokens and metrics, preview metadata, and every viewport variant declared by its surface policy. Surface/viewport keys remain distinct even when viewport names overlap. Changing only a top bar or rail is insufficient to define a profile.
- **REQ-003 — Exact capability coverage.** Every selectable profile shall cover the exact semantic destinations reachable for every registered surface. Registration derives and validates the complete `(profile, surface, viewport, destination)` product and rejects missing or extra coverage; a feature page may not silently fall back to another profile or surface.
- **REQ-004 — One layout-neutral state authority.** Business data, commands, navigation identity, selected conversations, drafts, active operations, permission behavior, and capability decisions shall live above layout widgets and remain unchanged by a presentation switch. Profiles receive only narrow immutable semantic snapshots and callbacks through shell and destination ports, never the complete `ClientController` or another application authority.
- **REQ-005 — Surface-aware adaptive resolution.** The selected profile identity shall remain stable while its variant is resolved from an explicit registered runtime surface, that surface's declared viewport policy, local constraints, and input/accessibility capabilities. Surface is a registry-key dimension, not a second profile identity. A surface never borrows another surface's chrome. Window size, device names, and orientation shall not silently rewrite the user's selection.
- **REQ-006 — Orthogonal appearance composition.** Appearance presets continue to own palette and light/dark selection. Layout bundles own structure, typography scale, density, shape, elevation, motion, styled chrome, and component recipes. The client shall compose the two axes deterministically without maintaining a layout-by-theme Cartesian product or resetting appearance during a layout switch.
- **REQ-007 — Transactional preferences.** Layout, appearance, and locale selections shall be loaded and saved through one typed presentation-preferences authority with serialized, atomic writes. Rapid updates cannot overwrite each other, and the first meaningful shell paint shall wait for preference hydration.
- **REQ-008 — Preview, commit, cancel, reset, and recovery.** A user can preview any registered profile, confirm it, cancel it, or reset to the one injected platform-preferred default. Only a confirmed selection is persisted. First run, missing or invalid stored identifiers, and unavailable profiles resolve through the same injected value with a user-safe diagnostic; persistence failure restores the prior committed layout.
- **REQ-009 — State and focus continuity.** Switching among registered profiles shall preserve semantic navigation, selected agent/session, editable drafts, running work, and restorable scroll/expansion/focus state. The implementation shall not keep every complete layout tree alive or move the entire tree with a global key.
- **REQ-010 — Accessibility and input parity.** Every registered bundle shall expose equivalent semantic actions, predictable focus order, the appropriate input/touch targets for its surface, text scaling, contrast, and reduced-motion behavior while preserving its frozen current rendering and interactions.
- **REQ-011 — Cardinality-independent bounded runtime.** Registry lookup by `(profile, surface, viewport)` and active-profile resolution shall be O(1) after bounded construction-time validation. Catalog, registry, manager, resolver, host, and Settings algorithms shall not change when `N` or `M` changes. Resolution caching is bounded by the active selection/environment/catalog revision; only the current bundle is built; rapid transitions are coalesced or serialized. Renderer or shared-feature code shall not branch on profile IDs; only immutable composition/catalog lookup may select a bundle by typed key.
- **REQ-012 — Hard bundle isolation.** Every surface bundle owns its source, shell, destination presentation, styled chrome and metrics, components, tokens, assets, preview, restoration namespace, fixtures, tests, goldens, and source manifest below its canonical profile/surface boundary. The shared layout root may contain only contracts, composition/catalog/registry, host/scope/focus infrastructure, and neutral ports; concrete style, components, metrics, or destination presentation may not be scattered through shared features or shell paths. A bundle may depend only on shared presentation contracts, narrow layout-neutral semantic state/command ports, localization, appearance color input, and explicitly style-free primitives. It may not import another bundle, the complete `ClientController`, legacy shell code, backend/platform implementations, shared styled chrome, shared visual metrics, or a visually opinionated component kit. Existing shared chrome shall be privatized with byte-equivalent constants/metrics and pixel-, semantics-, and interaction-equivalent output, then deleted in the same migration; no compatibility wrapper or fallback may remain. Static gates, isolated bundle suites, and pairwise change-impact checks shall prove that changing one bundle cannot change any other bundle's source manifest, golden output, or state.
- **REQ-013 — Retired-state reset and complete migration.** Retired identifiers, fields, preference namespaces, renderers, shared chrome authority, tests, and documentation shall remain absent. The current client shall initialize or recover only current-schema state; it shall not discover, import, rename, copy, translate, alias, or otherwise accept retired state as compatibility input. Superseded shell/controller bridges and duplicate authorities are deleted after direct cutover, with no long-lived compatibility path.
- **REQ-014 — Cardinality-complete verifiable delivery.** Contract, manager, store, widget, adaptive, state-continuity, accessibility, golden, source-manifest, integration, architecture, build, and launch checks shall prove the registered `N × M` product. Every bundle shall have behavior, adaptive, semantic, golden, and source-manifest coverage; production fixtures shall exercise representative Home, Agents, and Settings content; and for each bundle, change-impact checks shall prove all other `N × M − 1` bundles unchanged. Historical partial-scope receipts are non-current until rerun against the frozen registered-product baseline.

## Scope

- Platform-neutral contracts, registration-derived catalog/registry/Settings metadata, resolver, selection state machine, preference repository, presentation host, narrow semantic shell port, visual-token composition, destination registry, state-restoration policy, architecture verifier, and child-plan contracts.
- Every currently registered profile/surface bundle centralized at `frontend/layout/profiles/<profile>/<surface>/`, with corresponding profile-owned test and asset roots, revalidated as one exact `N × M` product.
- Settings discovery, preview, commit/cancel/reset, error feedback, unique catalog-default metadata, injected platform-preferred fallback behavior, and one current typed authority.
- Exact privatization of current styled chrome and metrics followed by deletion of the shared styled authority, without redesign.

## Non-goals

- Changing current layout design, including component appearance, arrangement, motion, labels, or interactions recorded in the baseline.
- Changing server policy, native-agent readiness, authorization, relay protocol, or feature availability.
- Loading executable layouts from portable data, a network service, or an arbitrary widget DSL.
- Discovering, importing, translating, or preserving retired layout identifiers, state roots, preference readers, renderer paths, or shared styled compatibility wrappers.
- Treating packaging, GitHub Release, or any store publication as proof of layout correctness.
- Keeping every profile mounted in an `IndexedStack` or using a whole-tree `GlobalKey` as the state model.

## Final acceptance target

The plan family is accepted when one registration-derived authority validates the exact `N × M` product; adding a profile changes only its independent bundles and one composition registration; the current baseline render, semantics, and interactions remain unchanged; catalog-default metadata and the injected platform preference remain separate authorities with distinct roles; renderer children own disjoint bundles behind narrow semantic ports; shared styled chrome and full-controller bridges are deleted after equivalent privatization; no renderer contains profile-ID branches; every registered bundle's behavior/adaptive/semantic/golden/source-manifest suite and representative Home/Agents/Settings fixture passes; and the full pairwise change-impact matrix proves each bundle independent of all others.
